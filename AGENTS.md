# Repository Guidelines

## Project Structure

- `src/` contains browser JavaScript, organized by page under `src/pages/` and shared helpers under `src/shared/`.
- `public/` contains hosted HTML and static assets. Edit source in `src/`; `public/dist/` is generated by webpack and must not be edited manually.
- `functions/` contains Firebase Cloud Functions (Node.js 22), with backend tests in `functions/test/`.
- Root `tests/` covers frontend behavior and Firebase Rules. Firebase configuration and security rules are in the repository root.

## Development and Verification

- `npm ci` installs frontend dependencies from the lockfile.
- `npm run dev` serves the site at `http://localhost:9000` and connects local browser sessions to the exam emulators. Production builds keep the production Firebase project.
- `npm run dev:exam:emulators` starts isolated Auth, Firestore, Functions, and Storage emulators; `npm run seed:exam:emulators` resets only the demo exam fixture.
- `npm run build` creates the browser bundles in `public/dist/`.
- `npm test` runs repository checks, frontend tests, and Auth/Firestore/Storage emulator tests using the demo project `demo-ipfest-p0`.
- `npm --prefix functions ci` installs backend dependencies; `npm --prefix functions test` runs Functions unit tests.

## Style and Naming

Follow the nearby code's JavaScript module style and indentation. Frontend page modules use descriptive kebab-case file names, with existing legacy exceptions preserved. Keep shared, reusable browser logic in `src/shared/`; keep Cloud Functions authorization and validation on the server. Avoid editing generated bundles or unrelated legacy files. No repository-wide formatter or linter is configured; keep diffs focused and readable.

## Testing

Frontend and backend tests use Node's built-in `node:test` runner and are named `*.test.js`. Add tests beside the existing suite (`tests/` or `functions/test/`); Rules behavior belongs in `tests/rules/access.test.js`. Run the focused test while iterating, then the relevant full command above. Never point emulator tests at the production project.

## Commits and Pull Requests

Recent history uses concise imperative subjects, often prefixed by a type and scope, such as `feat(delegates-relation): add search`. Use the same pattern. PRs should explain user-visible changes, link the related issue or plan when available, list verification commands and results, and include screenshots for UI changes. Call out Firestore/Storage Rules or Function deployment requirements separately.

## Security and Configuration

Do not commit secrets, service-account keys, or real participant data. Cloud Functions use the Admin SDK and bypass Firestore Rules, so each callable must validate authentication, roles, and resource ownership itself. Treat `.firebaserc` and local Firebase config carefully; local development does not imply emulator isolation.
